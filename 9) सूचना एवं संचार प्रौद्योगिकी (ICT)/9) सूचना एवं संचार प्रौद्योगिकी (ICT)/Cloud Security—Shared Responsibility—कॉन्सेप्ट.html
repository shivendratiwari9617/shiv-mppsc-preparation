# प्रस्तावना Cloud Security—Shared Responsibility के कॉन्सेप्ट का अर्थ यह है कि क्लाउड सेवा की सुरक्षा कुछ पर प्रदाता (Cloud Provider) की जिम्मेदारी होती है और कुछ पर ग्राहक (Cloud Consumer) की; यह विभाजन सेवा मॉडल (IaaS/PaaS/SaaS) के अनुसार बदलता है। MPPSC के परिप्रेक्ष्य में यह विषय महत्वपूर्ण है क्योंकि राज्य एवं केंद्र की e‑Governance सेवाएँ (MeghRaj/NIC‑hosted portals), UIDAI जैसे डेटाबेस और लाइव‑services पर भरोसा कर निर्भीक निर्णय लिए जाते हैं; अतः Shared Responsibility की स्पष्ट समझ, IAM/Key‑Mgmt/Encryption जैसी high‑yield तकनीकों का सही अनुप्रयोग और compliance अनिवार्य हैं। # अवधारणा एवं विकास Shared Responsibility मॉडल का मूल सिद्धांत यह है कि क्लाउड प्रदाता शारीरिक इन्फ्रास्ट्रक्चर, hypervisor, नेटवर्किंग और बेसिक प्लेटफॉर्म की सुरक्षा का नियंत्रण रखता है, जबकि ग्राहक OS, एप्लिकेशन, डेटा और कॉन्फ़िगरेशन की सुरक्षा का उत्तरदायी होता है। NIST की Cloud Computing Definition (SP 800‑145) और ISO/IEC 27017 जैसे मानक इस विभाजन को संदर्भित करते हैं। भारत में MeitY के माध्यम से 2014 में लॉन्च हुआ “MeghRaj / National Cloud” model राज्य‑स्तर पर क्लाउड अपनाने का मार्ग प्रशस्त करता है, अतः राज्य सरकारें (जैसे MP e‑Governance) को Shared Responsibility का पालन करना आवश्यक है। # तकनीकी संरचना और कार्यप्रणाली (IAM पर केन्द्रित) Identity and Access Management (IAM) Shared Responsibility का केंद्रीय हिस्सा है: क्लाउड प्रदाता Authentication infrastructure (identity provider, directory services) और API-level access control सुविधाएँ देता है; उपभोक्ता को RBAC/ABAC policies लागू करके least‑privilege सिद्धांत अपनाना होता है। तकनीकी घटक: Multi‑Factor Authentication (MFA), OAuth 2.0 / OpenID Connect (OIDC) for federated auth, SAML 2.0 for SSO, Privileged Access Management (PAM) और ephemeral credentials (short‑lived tokens)। प्रभाव‑विश्लेषण: यदि ग्राहक IAM misconfiguration करता है (उदा. over‑permissive IAM roles), तो data breach का जोखिम बढ़ता है—WAF/CloudTrail/Audit logs जैसी सेवाएँ provider देता है पर log review और alerting सामान्यतः ग्राहक का दायित्व है। # कुंजी प्रबंधन (Key Management) तथा Encryption (micro‑facts सहित) Encryption at‑rest और in‑transit दोनों Shared Responsibility के दायरे में आते हैं: प्रदाता आमतौर पर TLS 1.2/1.3 का समर्थन करके in‑transit सुरक्षा देता है और storage‑level encryption (AES‑256) जैसी सुविधाएँ उपलब्ध कराता है; ग्राहक को encryption keys की lifecycle, rotation, deletion और access policies नियंत्रित करनी चाहिए। Key Management Services (KMS), Cloud HSM (FIPS 140‑2/3 compliant) और Customer‑Managed Keys (CMK)/BYOK (Bring Your Own Key) विकल्प प्रमुख उपकरण हैं। Envelope encryption, key‑wrapping techniques और hardware root‑of‑trust cloud‑HSM द्वारा संभाली जाती हैं। नीति/अनुप्रयोग स्तर पर यह तय करना भी ग्राहक का काम है कि sensitive PII/biometric data (जैसे UIDAI) के keys कहाँ रखा जाए — provider‑managed KMS या ग्राहक‑हस्ताक्षरित HSM। # मानक, नियम एवं सरकारी परिप्रेक्ष्य Cloud security के लिए ISO/IEC 27017 (cloud security controls), ISO/IEC 27018 (PII protection in public clouds), NIST SP 800‑53/800‑145 आदि को स्वीकार्य मानक माना जाता है। भारत में CERT‑IN के दिशा‑निर्देश, MeitY की cloud adoption guidance और Digital India पहलें (MeghRaj/Meghdoot आदि) प्रमुख संस्थागत संदर्भ हैं; केंद्र सरकार ने सरकारी डेटा के लिए data residency और classification पर ध्यान देने को कहा है। राज्य स्तर पर MP e‑Governance प्रोजेक्ट्स को NCC/NIC के माध्यम से MeghRaj सेवाओं पर hosting हेतु security SLAs, incident response और periodic audit (VAPT) लागू करने का निर्देश देना चाहिए। # अनुप्रयोग और केस‑स्टडी (Governance, Health, Education) गवर्नेंस: e‑District, e‑Hospital और Aadhaar‑based authentication services में क्लाउड‑hosted modules पर Shared Responsibility लागू होता है—उदा., application‑level input validation और session management ग्राहक का जिम्मा है जबकि underlying virtualization security provider संभालता है। स्वास्थ्य क्षेत्र: cloud‑hosted EMR systems में HIPAA‑like controls और encryption keys का प्रबंधन अत्यावश्यक; प्रदेश स्वास्थ्य मिशन को patient data की encryption policy और key‑storage के लिए HSM/tenant‑isolation को अपनाना चाहिए। शिक्षा: MOOCs और centralized LMS में IAM federation (Shibboleth/SAML) लागू कर परिसर‑स्तरीय identities को सुरक्षित रखा जा सकता है। # जोखिम, चुनौतियाँ और वास्तविक‑दृष्टांत मुख्य जोखिम: (1) Misconfiguration (उदा. S3 public buckets) जो ग्राहक‑गलती से आती है; (2) Shared tenancy से जुड़ी side‑channel attacks; (3) Key compromise यदि key‑rotation और KMS controls कमजोर हों; (4) Compliance gaps λόγω data residency/sectoral regulations। तकनीकी micro‑fact: अनेक breaches में root cause misconfigured IAM policies या unrotated keys रहे हैं। प्रशासनिक चुनौती: सरकारी विभागों में cloud security awareness कमी (IAM policy design, use of service‑principals) और legacy applications का cloud‑migration में inadequacy। परिणामस्वरूप data exfiltration, service disruption और regulatory penalties संभव हैं। # समाधान, नियंत्रण एवं best practices (विश्लेषणात्मक सुझाव) पहला—Shared Responsibility को SLA में स्पष्ट लिखें; IaaS/PaaS/SaaS के लिए matrix तैयार करें जहाँ physical security, hypervisor सुरक्षा provider की और OS/patching, app security ग्राहक की स्पष्ट जिम्मेदारी हो। दूसरा—IAM का केंद्रित सुधार: RBAC + ABAC hybrid मॉडल, just‑in‑time privilege escalation, ephemeral credentials, mandatory MFA, और centralized identity federation (LDAP/AD federation with OIDC) लागू करें। तीसरा—Key Management Strategy: envelope encryption, customer‑managed CMKs with Cloud HSM (FIPS certified), automated key rotation (e.g., 90‑day policy), BYOK जब data residency/sovereignty कारण आवश्यक हो। चौथा—Encryption standards अपनाएँ: in‑transit TLS 1.2/1.3, at‑rest AES‑256, strong KDFs और signed certificates (PKI) के लिए CA management। पाँचवाँ—Continuous monitoring: CloudTrail/Stackdriver/Azure Monitor जैसे audit logs, SIEM integration, automated misconfiguration scanners और periodic VAPT + red‑team exercises। # नीति‑निर्देश और प्रशासनिक कार्रवाई का मार्ग राज्य सरकार को MeitY/NIC के मॉडल के अनुरूप cloud security policy बनानी चाहिए जिसमें विभागीय Shared Responsibility matrices, mandatory IAM baselines, KMS deployment norms और incident‑reporting timelines (CERT‑IN के मानदंड अनुसार) शामिल हों। procurement में security by design clauses, data residency clauses और independent third‑party audits को अनिवार्य करें। capacity building हेतु technical trainings (IAM, key management, encryption practices) और centralized Cloud Centre of Excellence (CoE) की स्थापना उपयोगी होगी। # निष्कर्ष और दीर्घकालीन दिशा संक्षेप में, Shared Responsibility का स्पष्ट ढाँचा ही cloud security की नींव है—जहाँ तकनीकी नियंत्रण (IAM, KMS, TLS/AES), मानक पालन (ISO/NIST) और सरकारी नीतियाँ (MeghRaj, CERT‑IN) साथ मिलकर सुरक्षा सुनिश्चित करती हैं। एक ओर यह model क्लाउड अपनाने को त्वरित और लागत‑प्रभावी बनाता है; दूसरी ओर यदि IAM/KMS और encryption lifecycle neglect हो तो संवेदनशील सरकारी डेटा जोखिम में पड़ सकता है। दीर्घकाल में राज्य‑स्तर पर centralized IAM, customer‑managed KMS with HSM, zero‑trust architecture और नियमित compliance audits अपनाना आवश्यक होगा ताकि MP की e‑Governance सेवाएँ सुरक्षित, विश्वसनीय और नियमपरक बनी रहें। स्रोत 1: NCERT (कक्षा 6–12) – विज्ञान/कम्प्यूटर विज्ञान/सूचना एवं संचार प्रौद्योगिकी के संबंधित अध्याय स्रोत 2: Arihant / Lucent – "Objective Computer Awareness" या समकक्ष ICT पुस्तक स्रोत 3: MeitY / Digital India – भारत सरकार का आधिकारिक ICT/e‑Governance पोर्टल
